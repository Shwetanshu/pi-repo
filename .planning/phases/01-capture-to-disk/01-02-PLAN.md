<objective>
Make adding a to-do lossless and crash-safe: an add appends to whatever is already in `todos.json`,
assigns the next id above every existing id, and replaces the file atomically so an interrupted write
can never truncate the user's list.

Purpose: 01-01 proved the path end to end but wrote the file in place with `fs.writeFileSync`.
That is the remaining data-loss window in the phase: a crash or a full disk mid-write leaves a
half-written file that Phase 2 would then have to reset — losing everything. This plan closes it and
pins down the identity contract that Phases 2 and 3 depend on.

Output:
- `lib/store.js` hardened: `readTodos` handles the empty/whitespace-only file, `appendTodo` writes
  through `todos.json.tmp` with `fsyncSync` and `fs.renameSync`, and cleans the temporary file on
  every failure path.
- The ID rule fixed as `max(existing ids) + 1` — stable, never reused, gaps preserved.

Depends on 01-01: that plan created `todo.js` and `lib/store.js`, resolved the on-disk shape at its
decision gate, and proved the single happy path. This plan changes only the store's internals, so the
CLI contract established there does not move.

Requirements: STOR-01 (items persist to `todos.json` in the current working directory) and IDNT-01
(each item gets a stable id at creation, never reused). RUN-01 stays satisfied — this plan adds no
dependency.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `todos.json` on disk → `lib/store.js` | The file may be hand-edited, written by another tool, truncated by a previous crash, or be something other than an array. Its contents are untrusted and must not be trusted to be well-formed. |
| `lib/store.js` → filesystem | The process rewrites a file in a directory it does not own, may be interrupted mid-write, and may find `todos.json` or `todos.json.tmp` already present in any form. |
| concurrent processes → `todos.json` | Two invocations in the same directory can interleave their read-modify-write cycles. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05 | Tampering | `lib/store.js` `appendTodo` — whole-file rewrite interrupted mid-write | high | mitigate | Write to `todos.json.tmp` opened with `flag: 'wx'`, `fs.writeSync`, `fs.fsyncSync` before `fs.closeSync`, then `fs.renameSync` over the target — the replace is atomic at the filesystem level, so a reader or a crash sees either the old complete file or the new complete file, never a truncated one. The `catch` closes the descriptor, unlinks only the temp path, and rethrows, so the original survives every failure path. Task 1 asserts no `.tmp` survives. |
| T-01-06 | Tampering | `appendTodo` read-modify-write under two concurrent invocations | medium | accept | No file locking by design: two simultaneous adds can both read the same array and the later rename wins, so one record is lost. | T-01-07 | Tampering | `readTodos` — a non-array or unparseable `todos.json` reaching `appendTodo` | high | mitigate | `readTodos` throws before any write begins, and `appendTodo` calls it first, so no serialization or rename ever happens for a file it could not read.
